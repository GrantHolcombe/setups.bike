# It Pays To Know The Strava Line

*Riders say it pays to know the Strava line: the route through a trail that local knowledge
says is fastest on the leaderboard. An AI agent can ride any line you point it at. Knowing which
line to take is the developer's job, and this log is where I wrote down the lines I chose.*

I built Setups.Bike by hand starting in July 2024: the React and MUI front end, the
API Gateway and Lambda back end, the Postgres database, and the AWS hosting and deploy pipeline.
In November 2026 I brought in an AI coding agent (Claude Code) as a tool to speed up
development. I used it to harden what I'd built (auth, a least-privilege database role, an AWS
cleanup), to add the Pro plan and its features, and to write tests and docs. The architecture
and the product were already mine; the agent made a solo project move like a small team.

This log records the calls I made once the agent was involved: where I steered, corrected or
overruled it, set its limits, or weighed a trade-off myself. It sits next to the code because the
code shows *what* was built; this shows the engineering judgment behind it.

Newest first. Each entry: the situation, what I decided, and why.

---

## How I work with the agent

Standing rules, set early and kept throughout:

- **Least privilege for the agent too.** The agent reaches AWS as an IAM user
  (`claude-readonly`) with read-only access plus a custom policy that allows only the operations
  the project needs. It explicitly denies IAM writes, billing, domain changes, Secrets Manager
  reads and deleting the live site buckets. Anything outside that, like deleting IAM roles, I do
  myself in the console, from commands the agent prepares and I review first.
- **No secrets in chat.** Passwords, keys and connection strings never pass through the
  conversation. When a secret has to move (for example into a Lambda's env vars), the agent
  copies it inside AWS and reports only true/false checks, or I enter it myself. Passwords are
  generated by the provider (Neon, Stripe), not typed by me or the agent.
- **I approve every deploy and every delete.** The agent asks before any push that deploys the
  site and before deleting anything. I batch deploys myself.
- **Prove it before removing the fallback.** Risky changes go out alongside the old path, get
  tested, and only then is the old path removed, with a published Lambda version kept for
  rollback.
- **Docs stay current.** Roadmap, database notes and the style guide are updated in the same
  change as the code, and tracked on a GitHub Project board.

## 2026-11-20: Privacy-first analytics, with sign-up source kept in memory only

**Situation:** Marketing needs numbers before the first sticker or post goes out: visits,
sign-ups, and which campaign brought each sign-up. I asked to be told whenever the work would
bring in GDPR requirements.

**Decision:**
- **Visits:** Cloudflare Web Analytics, which uses no cookies, no fingerprinting and stores no
  IP addresses. Activity dates are counted in the app's own database.
- **Sign-up source:** a campaign tag (from a QR code or partner link) is kept **in memory for
  that visit only** and saved with the account only if the person signs up then. It is never
  stored in the browser. Ad click IDs are skipped until ads actually start.
- **Privacy Policy:** updated before any of it goes live.

**Why:** Storing a tag in the browser for 30 days would catch more returning visitors. But for EU
visitors, storing non-essential data on the device generally needs a consent banner. Memory-only
avoids that, and the trade-off (a sign-up days later isn't attributed) is small at this stage.
It can move to 30-day storage later with a small code change and a one-line policy update.

## 2026-11-19: End-to-end tests with Playwright

**Situation:** After moving the Lambdas to a new database role, the plan was for me to click
through the app by hand to confirm it worked.

**Decision:** Automate that check instead, as a Playwright suite that drives the real app against
the live API and database (`e2e/`). I asked first whether the existing unit tests already
covered it. They don't: the Jest tests mock the API, so they would pass even if a Lambda had
lost a database grant.

**Why:** The app is growing, and a manual click-through doesn't scale or get repeated. Details I
chose or approved:
- A **dedicated test Google account**, comped to Pro, so tests never touch my real data.
- Sign in **once by hand** and reuse the saved session, rather than adding a test-only login
  backdoor to the Lambdas.
- Tests clean up after themselves.
- It runs locally before deploys, not in CI yet, because it writes to production.

The first run passed all 13 tests and confirmed the new database role's permissions.

## 2026-11-19: Upgrade Node 16 to 26

**Situation:** Tooling warned that Node 16 was too old (Lighthouse earlier, Playwright now). I'd
already planned to upgrade.

**Decision:** Upgrade local dev and CodeBuild together to Node 26 LTS, and track the Lambdas'
`nodejs20.x` runtime (end of support April 2026) as its own roadmap item.

**Why:** Node 16 has been end-of-life since 2023. Keeping local dev and CI on the same version
avoids "works on my machine" builds. I verified the unit tests and the production build before
changing CI.

## 2026-11-19: Rename the database env vars from `RDS_*` to `NEON_*`

**Situation:** While swapping the Lambdas to the new database role, every Lambda's env vars were
being edited anyway. They were still named `RDS_*` from when the database ran on AWS RDS/EC2.

**Decision:** Rename them to `NEON_*` in the same change, knowing it meant redeploying all 13
Lambdas.

**Why:** Stale names cause confusion later ("is there still an RDS instance?"). The cost was
lowest while the variables were already being touched and tested.

## 2026-11-19: One least-privilege database role, with Neon-generated passwords

**Situation:** All Lambdas connected to Neon as the database owner, which can drop tables and
change grants.

**Decision:** Before building it, I asked whether this meant one user and password per Lambda,
and whether migrations could still run as the owner. We settled on:
- **One app role** (`setupsbike_app`) for all Lambdas, allowed only to read and write rows.
- **The owner login kept for migrations only**, held by me alone and rotated afterwards.
- Neon's **Reset password** generates both passwords, instead of me picking them.

**Why:** A role per Lambda would mean 13 passwords to manage for little gain, since all the
Lambdas need the same table access. One app role removes the real risk (a leaked Lambda
credential being able to destroy the schema). Provider-generated passwords are stronger than
anything typed, and never have to be seen.

## 2026-11-19: A style guide, and database docs beyond the schema dump

**Situation:** The UI had grown one screen at a time, and the dialogs had drifted apart in
layout, button order and wording. The only database documentation was `db/schema.sql`, a raw
dump that says what the columns are but not what they mean or how the tables connect.

**Decision:** Write both down as living docs:
- **[Style guide](STYLE_GUIDE.md)** covers color tokens with contrast rules for light and
  dark mode, type, spacing, the one dialog pattern, buttons, inputs, feedback messages and
  cards. The existing dialogs were then brought into line with it.
- **[Database doc](DATABASE.md)** has an entity-relationship diagram generated from the schema
  (`npm run db:diagram`, so it can't drift from the real tables), plus notes on what each table
  is for, which Lambdas use it, its indexes and triggers, and the roles.

**Why:** When an agent writes much of the code, its "memory" of conventions is whatever is
written down. A style guide makes new screens match without re-explaining the rules every
time, and reviewing a change against a written standard is faster than going by gut feel. A
generated diagram stays accurate, and the table notes record the meaning a schema dump can't.
Both double as onboarding docs for anyone reading the repo.

## 2026-11-20: Don't restrict Neon by IP address

**Situation:** The roadmap had "limit which IPs can reach Neon" as a hardening step.

**Decision:** Not doing it, and doing the least-privilege role instead.

**Why:** IP Allow is on Neon's Scale plan only, and Lambdas have no fixed IPs without a NAT
gateway (about $30+ a month), for an app that costs pennies to run. A least-privilege role
gives most of the protection for free.

## 2026-11 (PWA): An ordered list for the iPhone install steps

**Situation:** The "Add to Home Screen" instructions for iPhone had a layout problem, and the agent
proposed fixing it with a column layout.

**Decision:** I suggested an ordered list (`<ol>`) instead.

**Why:** The steps are a sequence, so the markup should say so. An ordered list is numbered,
screen readers announce it as steps ("list, 3 items"), and it can't fall apart on narrow phone
screens the way a column layout can. The semantic fix also turned out to be the simpler one.

## 2026-11-18: Batch deploys, and check the real cost

**Situation:** Every push to `main` runs the CodePipeline/CodeBuild deploy, and the month had used
up the free build minutes.

**Decision:** Test frontend changes locally against the live API first, then bundle several
into one deploy that I approve. I also had the agent check the real deploy cost in AWS billing
instead of relying on estimates.

**Why:** It keeps CI cost near zero (a deploy turned out to cost about 1-2 cents) and means each
deploy is a tested batch, not a stream of small pushes. Once the real numbers showed the cost
was negligible, I dropped the cost estimates but kept the approval step.

## 2026-11-18: Defer "suggested settings" over liability

**Situation:** Phase 2.4 of the roadmap was to suggest suspension settings to riders.

**Decision:** Deferred.

**Why:** Settings that come from the app read as a recommendation, and a wrong one can hurt
someone on a bike. Shared setups carry a clear notice that they come from another rider, not
from Setups.Bike.

## 2026-11-18: Keep Pro private until the Pro features are built

**Situation:** Billing (Stripe) was built and working in test mode.

**Decision:** Keep Pro switched on for my account only (`BILLING_ENABLED_FOR`) until the Phase 2
features were built and tested, then launch. My own account is comped in the database (no fake
Stripe subscription), and I made a real purchase on the live account to test it end to end.

**Why:** Charging for Pro before it had features worth paying for would have been a poor first
impression. A per-user switch let me test real billing in production without exposing it.

## 2026-11-20: All rights reserved

**Situation:** The repository is public as a portfolio piece, and the app is a paid product.

**Decision:** No open-source license. A `LICENSE` file states all rights reserved, plus a line in
the README.

**Why:** Visitors can read the code to judge my work, but have no right to reuse it in a
competing app.

## 2026-11-13 to 11-20: Shrink the AWS account to what the app uses

**Situation:** The account held years of leftovers: an EC2-hosted database, RDS-era IAM roles,
2018-19 test projects, and orphaned policies. It cost about $31 a month.

**Decision:**
- Move the database to Neon.
- Delete everything unused, after the agent audited what each resource was attached to.
- Make IAM deletions myself, from reviewed commands.

**Why:** Less attack surface and a bill of about $0.05 a month. Each step was verified, and a
local backup of the old database was kept before the server was terminated.
